# CLAUDE.md

Guidance for Claude Code working in **Arts Color Switcher for Elementor**.

## What this is

Scroll-triggered palette switching for Elementor. Every Global Color gains an **Alt** value, one registered scalar (`--arts-cs-p`, 0→1) morphs the whole page between the two, and sections marked as *zones* drive that scalar as they cross a trigger line.

Shape: a TypeScript engine (`src/ts/`) over a thin PHP shell (`src/php/`) that registers controls, enqueues assets and renders the toggle's markup — every color is computed in CSS, emitted through Elementor's own kit control `selectors`, so anything already linked to a Global Color animates for free.

Raster images ride the same seam: every image `MEDIA` control on the site is re-typed to `arts_cs_media`, which carries an Alt file as extra sub-keys of the control's own value and emits it through Elementor's `selectors` — no HTML filtering, no DOM writes.

It deliberately ships NO palette of its own and NO per-zone target theme: a zone always shows the opposite of the page baseline — the seam the dark-mode toggle drives by moving the baseline, so every zone inverts with it.

## Config gotchas

- **`knip.jsonc` and `.fallowrc.jsonc` take comments;** use them for per-entry reasoning.
- **Adopting a shared config means merging it, not replacing it.** Repo-specific entries hide in these files — a security `overrides` pin, a plugin-check ignore code, an extra workflow trigger. Diff the old file against the new one before deleting anything; CI will not tell you what you dropped.
- **Any dependency with an install script needs an explicit `allowBuilds` decision.** Adding `@wordpress/env` is the usual trigger — see the commented entry in `pnpm-workspace.yaml`.
- **`composer.lock` resolves dev deps against YOUR PHP, not `Requires PHP`.** The locked doctrine/instantiator declares `"php": "^8.4"` against the 8.0 floor; `require-dev` carried a `^1.5` pin until a Renovate bump moved it to `^2.0`. This repo's canary passes `integration_suites: '[]'` (plugin-check only), so no CI leg runs PHPUnit under 8.0 — re-check before trusting it there.

## Architecture

- **`src/php/Plugin.php`** — composition root. Extends `Base\Plugin` (arts/base `BasePlugin`), runs on `plugins_loaded` priority 20, wires the managers: `assets` (handles, the polyfill dependency, the pre-paint head script), `documents` (page-theme control + the baseline attributes), `elements` (the container/section control section), `elementor` (one Elementor cache clear per plugin version, widget registration), `kit` (Alt swatch injection), `media` (the Alt image control), `toggle` (every skin's markup + the shortcode).
- **`src/php/Controls/AltMedia.php`** — `Control_Media` subclass, type `arts_cs_media`. Owns the Alt sub-keys, the panel's words (as a control arg, so they stay translatable), and `get_style_value()`.
- **`src/php/Managers/Media.php`** — registers that control and re-types every image media control on the site as each section closes.
- **`src/ts/editor/altMedia.ts`** — the editor view: injects the Alt button into the stock control's own tools row and owns a second `wp.media` frame.
- **`src/php/Widgets/Toggle.php`** — the visitor-facing control, one widget with four Elementor skins in `Widgets/Skins/`. The skins are adapters: each calls `render_skin()`, which calls the `toggle` manager, so the shortcode draws exactly the same shapes.
- **`src/ts/boot.ts`** — frontend entry. Registers the `element_ready` hooks, gates handler attachment on a `data-settings` regex outside the editor, publishes `window.ArtsColorSwitcher`.
- **`core/zoneHandler.ts`** — the Elementor frontend handler: control values → an `IZone`, and it owns the resize/breakpoint watch.
- **`core/coordinator.ts`** — page-level state owner. Holds every zone, owns every IntersectionObserver, writes the ONE `<html>` attribute.
- **`core/resolve.ts`** — pure. Zone snapshots + baseline → `{ theme, scrubbingIndex }`, no DOM.
- **`core/scrollDriver.ts`** — the scrub, in three tiers: Arts Horizontal Scroll's published timeline, native CSS view-timeline, then WAAPI over the shared polyfill.
- **`core/horizontal.ts`** — the pinned-track probe, stage lookup and RTL flag for Arts Horizontal Scroll, in one place because the coordinator and the scroll driver must agree on whether an element is travelling sideways.
- **`core/preference.ts`** — the visitor layer. Owns the cookie (`write()` / `clear()` are its only writers) and mirrors it onto `<html>`.
- **`core/toggle.ts`** — every skin's presses and announcements. Skins differ only in how a press maps to a preference; what looks active is CSS's job.
- **`editor/index.ts`** — its own bundle: one `hookUI.After` over `document/elements/settings` that keeps the preview honest.
- **Everything else:** `src/styles/` (one partial per concern; `index.scss` is the sass entry), `src/ts/constants/` plus one-per-file `interfaces/` (`I*`) and `types/` (`T*`), `src/php/Base/` (typed shims over arts/base; `ManagersContainer`'s `@property` list mirrors `Plugin::get_managers_classes()`), `src/wordpress-plugin/` (plugin header, `readme.txt`), `.wordpress-org/` (wp.org assets and the Playground blueprint), `dev/seed/` (page seeders run by the e2e `global-setup.ts`: `demo-page.php` pins the element ids and zone counts the specs assert, while `preview-page.php` is the Playground shop window, not an e2e fixture), `tests/ts` (vitest; `*.dom.test.ts` run under happy-dom), `tests/php` (wp-env PHPUnit), `tests/e2e` (Playwright). `src/php/libraries/`, `dist/` and `vendor-prefixed/` are gitignored build output — edit the sources.

## Frozen contracts (never rename after first release)

- PHP namespace `Arts\ColorSwitcher`; Strauss prefix `ArtsColorSwitcher\`; slug and text domain `color-switcher-for-elementor`; version constant `ARTS_COLOR_SWITCHER_PLUGIN_VERSION`.
- Asset handles `arts-color-switcher` and `arts-color-switcher-editor`, plus the SHARED `scroll-timeline-polyfill` (first registration across Arts plugins wins).
- DOM: `data-arts-cs` and `data-arts-cs-pref` on `<html>`, `data-arts-cs-baseline` on the Elementor document wrapper; classes `arts-cs-morphing`, `arts-cs-scroll-native`, `arts-cs-scroll-reverse`.
- The toggle's markup: class `js-arts-cs-toggle` on every skin's root, carrying `data-arts-cs-toggle` (the skin id), `data-arts-cs-mode`, `data-arts-cs-name` and `data-arts-cs-label-{system,default,alt}`; `data-arts-cs-set` on a Buttons option. Skin ids `icon`, `switch`, `buttons`, `dropdown` — Elementor stores them in `_skin` and suffixes `data-widget_type` with them, so a rename orphans saved widgets AND silently un-hooks boot.
- Custom properties: `--arts-cs-p` (the scalar), `--arts-cs-duration`, `--arts-cs-ease`, `--arts-cs-admin-bar`, the per-color `--arts-cs-c-{id}` / `--arts-cs-c-{id}-alt` pair, and the timeline name `--arts-cs-zone`.
- Events fired: `arts-cs:change` (`detail: { theme, source }`) and `arts-cs:settings-sync` (editor-only). Consumed: `arts/ajax/transition/sync/before`, `arts-hs:ready`. Filter consumed: `arts/scroll_timeline_polyfill/skipped_styles`.
- Control type `arts_cs_media`, its value sub-keys `arts_cs_alt_url` / `arts_cs_alt_id`, and its label arg `arts_cs_alt_labels`. The sub-keys are the hardest of these to change: they live INSIDE other widgets' saved settings, so a rename after release is a data migration across every `_elementor_data` blob rather than an edit. Pinned across languages in `tests/ts/phpParity.test.ts`.
- Control ids `arts_cs_enabled`, `arts_cs_viewport`, `arts_cs_viewport_hint`, `arts_cs_page_theme`; section `section_arts_cs`; kit repeater field `color_alt`; option key `arts_color_switcher_version`; cookie `arts_cs_pref`; shortcode `arts_color_switcher_toggle`.
- `window.ArtsColorSwitcher` and its `contract` number — README.md's Integration contract table is the published, public subset of this list, and `contract` bumps only on a breaking change to that table.

## Decided — don't reintroduce or "fix"

- **`arts_cs_enabled` is a `SELECT` (No/Yes), not a `SWITCHER`.** An off state of `''` is read by Elementor's responsive inheritance as "unset", so mobile would inherit the desktop "on". Both states must carry a real value or "off on mobile" is inexpressible.
- **`arts_cs_viewport` is NOT responsive** (`add_control()`, not `add_responsive_control()`; the comment in `Managers\Elements::add_section_controls()` says why). The per-device need is "don't run it here", which the enable control covers.
- **Zone state comes from an IntersectionObserver, never from a scroll listener.** The trigger line IS the observer's root, collapsed to a 1px full-width strip. That is what makes zones correct on both axes: a panel pinned inside a horizontal track has a frozen vertical band and moves only sideways, so a `getBoundingClientRect()` comparison reports it as on screen for the entire pin. Do not reintroduce a scroll pass — performance was never the reason; correctness was.
- **Inside a pinned horizontal track the strip is ROTATED** — a 1px column across the stage rather than a row across the viewport — so the Viewport handles keep the meaning they have vertically: how far into the screen the section travels before switching. A pinned panel spans the whole track height for its entire traversal, so any horizontal line is always crossed. The line is measured across the WRAPPER, never the track: the track is the thing being translated, so a line on it slides along with the content it is meant to measure.
- **The strip is full-width on purpose** (upright case). A centre-point root (the sibling plugin's scrollspy trick) would give free exclusivity between horizontal panels, but a vertical zone narrower than half the viewport would then never intersect it.
- **The frontend bundle is enqueued unconditionally.** A gate that inspected `_elementor_data` cost more per request than the few KB gzipped it withheld, and the bundle is inert without zones since boot gates its own handler attachment (full reasoning on `Assets::enqueue_frontend()`). Do not reintroduce a document-data gate.
- **Authority runs visitor, then author, then device.** A cookie always wins; its PRESENCE is what transfers authority. With no cookie the page's own setting decides, and only where the author declined to set one — `arts_cs_page_theme` on its `THEME_AUTO` default — does the device get a say, being the only party that knows the visitor's real sunrise and sunset. That is also why there is no scheduling feature and never will be: a server has one clock and its visitors do not. The precedence table is stated twice, in `resolveBaseline()` and in the head script PHP composes; `tests/ts/headScriptParity.dom.test.ts` executes the real emitted script against the real resolver over every combination, because if they drift the page changes theme between first paint and boot.
- **A two-state control releases, it does not pin forever.** Press once to store a choice, press again to DELETE the cookie — putting the visitor back exactly where they were before their first press. Deliberately not `write('system')`: what that place IS depends on the page (the author's palette where they pinned one, the device's where they did not), and either way it is somewhere the visitor has already been. That is the whole two-state-vs-tri-state argument, and the authority rule above leaves it unaltered.
- **The editor canvas never follows the author's device.** `followsDevice()` in `coordinator.ts` gates the Auto resolution on `isEditMode()`. Without it an author on a dark machine opens a light page, finds it dark, and designs against colors none of their visitors asked for. The OS watcher is safe for free because it calls `coordinator.refresh()` rather than forcing a theme — one precedence table, one place it can be wrong.
- **A control inverts the BASELINE, never `getTheme()`.** A zone on screen shows the opposite of the baseline, so reading the applied theme there stores the opposite of what the visitor asked for: the first press appears to do nothing and the second brightens the page. `coordinator.getBaseline()` exists for this and is deliberately NOT on the public contract.
- **What looks active is decided in CSS off `<html>`, not by the script.** The head script stamps `data-arts-cs-pref` before first paint, so a cached page never shows one visitor's control in another's state. The Switch's knob rides `--arts-cs-p` itself (`--arts-cs-seg-index: var(--arts-cs-p)` on its track — zero script), so it glides in lockstep with a binary morph and tracks a scrub, which the attribute deliberately never flips for (`resolve.ts`: flipping it would snap the scalar). Its transform transition is zeroed in `_switch.scss` — the shared 0.3s would chase per-frame scrub values. Only `aria-checked` stays discrete off `data-arts-cs`; ARIA cannot meaningfully interpolate. The one exception is the Dropdown — CSS cannot SET a `<select>`'s value, so `toggle.ts` corrects `select.value` at boot.
- **The Dropdown's list is a customizable-select enhancement, gated by `@supports (appearance: base-select)`.** SCSS owns the opt-in and the zero-config card in `_dropdown.scss` (browsers without support keep the platform picker, safely outside the gate); the List section owns author values. The card is `Canvas`/`CanvasText` plus `currentcolor` mixes because the plugin ships no palette — the `color-scheme: dark` flip in `_state.scss` is what turns it. A `::picker()` selector (`PICKER`) is never comma-joined into a legacy key (`BOX`, `LABEL`, `OPTION`): a browser without the pseudo drops the whole list, taking the legacy rules with it.
- **ARIA follows the visual affordance.** `role="switch"` only on the Switch skin, `aria-pressed` on the Icon and Buttons skins: a pressed button is the safer reading of anything that looks like a button. The Buttons skin is `role="group"` + pressed buttons rather than a radiogroup because it deliberately may have nothing chosen — "neither pressed" is how two options express the third state.
- **Joined and Separate are told apart by movement, not chrome.** Joined is one track with a single mark that travels to the pinned option; Separate is independent buttons where the pinned one carries its own fill. Both were once a border and a gap apart, which read as the same control with different padding.
- **The segmented geometry is derived, never hardcoded** — the same model as the pricing switcher on artemsemkin.com, which is the same control. Three numbers state it: `--arts-cs-seg-pad`, `--arts-cs-seg-gap` and `--arts-cs-seg-count` (emitted inline by PHP, since the count is the one thing CSS cannot work out); the mark's width and travel are computed from them in `_segmented.scss`. Halves and thirds hardcoded per mode went wrong the moment a gap existed, which is why the Spacing control writes `gap` AND `--arts-cs-seg-gap`.
- **There are no divider lines — a seam is the buttons' own borders meeting, and "flush" is derived, not queried.** Joined once drew dividers derived from its track border; they were cut (the travelling mark already marks the boundaries, and mixing them with Separate's per-button borders read as two line systems). In Separate, `--arts-cs-seg-flush` is 0 flush and effectively infinite at any spacing, so `min(value, flush)` states "only while flush" as arithmetic — no style query, every browser. The `min()` rules are emitted by the controls themselves (`option_border` `fields_options`, `option_radius` selectors): a plugin-stylesheet longhand can never outrank the `{{WRAPPER}}`-scoped shorthand it must beat.
- **Those variables are declared on the ROOT, not the track.** Custom properties inherit, and the track is not always the same element: the Joined root IS its own track, the Switch's is a child. Re-declaring them on the track is what made the Spacing control dead on the Switch.
- **The track is an inline GRID, not a flex row** (why: `_segmented.scss`). Nothing is given a size either — the Switch track is what its icons make it, so Icon Size, Track Padding and Spacing are its only dimensions, and the mark's colour is one custom property (`--arts-cs-toggle-active`) so a single control reaches it wherever the layout puts it.
- **Empty means absent, and the state count is STATED, never derived.** The label controls carry real defaults an author can delete rather than placeholders, and deleting one prints nothing — including an empty `<option>` in the Dropdown. How many states a control offers is the `mode` control, offered to every skin but the Switch (a knob has no third position); deriving it from whether the System label had a word broke once icon-only options existed. A Buttons option with no icon and no word falls back to the announced name rather than rendering empty. The built-in words (System / Light / Dark) survive only as the ANNOUNCED name, where no author can see them and an unnamed control would be unusable. The panel keeps the Default/Alt vocabulary in its control names; what a visitor reads says Light and Dark.
- **Style controls live on the WIDGET, in one Normal / Hover / Active tabs group per part (icon, label, track, list) — never in the skins.** `Skin_Base::start_controls_tabs()` assembles a `_skin` condition into a local variable it then never passes on, so the tabs WRAPPER is registered unconditioned while every tab header and field inside it is correctly scoped. Four skins each opening a group would leave three empty tab wrappers in the panel (the rest of the case is on `Widgets\Skins\Skin`). Declared on the widget each part has one group, one owner, and plain `_skin` conditions do the scoping. `Controls_Stack::start_controls_tabs( $id, array $args = [] )` DOES accept args, so a tab header can be conditioned — the Active tab is, since an icon that is the whole control has no "other" to be distinguished from.
- **No built-in state dimming.** The skins put no opacity of their own on icons or words — a dim composing on top of the colour controls means the Normal colour an author picks is never the colour that renders, with no control to say otherwise. Every state a dim would fake is expressible through the existing Normal/Hover/Active colour controls; the zero-config marks are structural instead — the knob's position, the pinned option's fill, the Icon skin's swap. Mechanical opacity stays — the hidden knob, the dropdown card's open animation.
- **Hover never repaints what is already chosen.** The Buttons skin states this as selector correlations between the `<html>` attribute and the element's own — the lists composed by `Widgets\Toggle::option_states()` and the `icon_hover()` / `icon_active()` / `label_hover()` / `label_active()` methods. The Switch states it as ARITHMETIC: its icon paint is a `color-mix` of the author's Normal/Active/Hover values weighted by `--arts-cs-p`, blended in `_switch.scss` off vars (`--arts-cs-sw-icon{,-hover,-active}`) the colour controls emit on the Switch root, so a fully chosen icon is untouched by construction. Never key Switch paint off `data-arts-cs` — a scrub deliberately never flips it, so attribute-keyed paint lit the wrong icon for the whole band a scrub held.
- **Never put the Switch blend in a control's value template: a Global-linked value BYPASSES `{{VALUE}}` templates.** `add_control_rules()`, reached via `add_control_style_rules()`, rewrites everything between `:` and `;` to the bare global var (elementor `core/files/css/base.php`), so only `property: {{VALUE}}` shapes survive linking. It compiles fine with a literal hex and collapses the moment a Global is linked, which is why the e2e seed alone cannot catch it.
- **Never gate anything on a STYLE QUERY over the scalar** (`@container style(--arts-cs-p: …)`): a `pointer-events` guard built that way stuck wrong both ways and bricked the control.
- **Condition a section AND every control in it, for two different reasons** — the docblock on `Widgets\Toggle::register_general_style()` states them, and `DarkModeTest::test_every_style_control_carries_its_own_condition()` pins the result.
- **State a control's own condition as `conditions` (plural) whenever its set is narrower than its section's.** A section's `condition` is merged into each of its controls BY INDEX, so a shorter list silently widens while a scalar replaces cleanly (`Widgets\Toggle::icon_active_conditions()` and its docblock; the `option_radius` pin in `DarkModeTest` is the regression test). Every nested condition in that file is composed from `any()`, `all()` and `term()`, and `term()` OMITS the `operator` key when there is none, so PHP and the editor's JS have one shape to agree about. `DarkModeTest::test_every_nested_condition_states_its_full_shape()` pins those arrays in full — the other assertions in that file only substring-match the JSON, which cannot see term order or a dropped operator.
- **A test that reads tab structure has to run under the editor's conditions** (`Performance::$is_frontend` false) and rebuild the stack, not just flip `set_use_style_controls()` — `DarkModeTest::editor_controls()` does exactly that.
- **No widget control ever takes a colour PAIR.** A second colour for the other theme is the per-element two-value configuration this plugin exists to remove. Every colour control takes one value, the author links it to a Global Color, and the Alt swatch in Site Settings turns it — which is the whole architecture, and the reason the plugin ships no palette of its own.
- **A control whose effect the author cannot see is not offered.** The label controls appear only on the Buttons and Dropdown skins, which print the words; on Icon and Switch they would change the tooltip and what a screen reader announces, which reads as a dead control in the panel. There is no control for the group's accessible name at all, for the same reason. Both still render — from the translated defaults — so nothing is unnamed. The shortcode keeps them all: it is a power-user surface, not a panel.
- **Visitor-facing words come from PHP, never from the script.** They were hardcoded English in `toggle.ts` and spoke the author's vocabulary ("Alt colors" names a slot in Site Settings and means nothing to a reader). PHP renders them into `data-arts-cs-label-*` where TS reads them: translatable through the normal .po path, with no `wp_set_script_translations` and no JSON translation files to ship — and authorable, which covers the site whose Alt palette is the lighter of the two.
- **Alt images RE-TYPE the media control; they do not add a sibling.** Same shape as `~/Projects/Framework/packages/ArtsEnhancedURLControl`, which does it for every URL control in production. A new type name is also why `elementor.addControlView` cannot collide with another plugin: only we claim our type. Never override the stock `media` type.
- **Everything is upgraded once any Alt swatch exists (`has_alt_colors()`, same gate as the head script); the per-control test is `media_types` containing `image`.** No widget allowlist. An Alt for a video or file picker means nothing.
- **The scan reads BOTH stack buckets, never `get_controls()`.** `add_control_to_stack()` files a control carrying `selectors` into `style_controls` whenever `Performance::should_optimize_controls()` is true, and `get_controls()` merges that bucket back only while `Performance::is_use_style_controls()` is true — which Elementor sets during a CSS file rebuild. Two independent flags, so a bare read is blind to `background_image` on a frontend request, which is the control that most needs seeing. `Controls_Manager::get_element_stack()` returns both.
- **A re-typed control carries `control_type => 'content'`.** Adding `selectors` to one that had none — the Image widget's own — would otherwise make it a style control, filed into the `style_controls` bucket, so a dynamic-tagged image would silently stop resolving at render (the full reason is in `Managers\Media::upgrade_media_controls()`). `is_style_control()` returns false outright for that arg; `AltMediaTest` pins that the Alt CSS is still generated by running the real generator.
- **The Alt rule is DERIVED from the control, never written here.** A declaration containing `{{URL}}` is mirrored verbatim under `html[data-arts-cs="alt"] ` with the placeholder swapped, so this plugin names no CSS property. A control with no declaration prints an `<img>`, so it gets `content: url(...)` on `{{WRAPPER}} img`. That second branch is correct only for single-image widgets; carousels and galleries are deliberately out of scope.
- **Originals stay FIRST in the merged `selectors` array.** An unset Alt costs the widget nothing only because its own rules are already written by the time ours bails (the docblock on `Managers\Media::alt_selectors()` has the mechanism). Pinned by generating real CSS, not by asserting array order.
- **The kit is skipped by the scan outright.** Its tabs are `Sub_Controls_Stack` proxies that forward `end_controls_section()` to the kit, so a tab closing fires the scan with the KIT as the registering stack, mid-`register_controls()`. Reading the Alt-swatch gate there re-enters `Base_Object::ensure_settings()`, which caches only once `get_init_settings()` returns — so the nested read can cache a half-registered snapshot of the kit's settings. Bounded, not infinite, and still not worth an Alt picker on the Site Logo.
- **Images swap abruptly; there is no cross-fade.** Keyed off `data-arts-cs`, which a scrub deliberately never flips, so an image holds through a scrubbing zone and swaps only on a settled transition. A fade needs a second painting surface and is a different feature — and the escape hatch you would reach for, a style query over `--arts-cs-p`, is already ruled out above.
- **No `object-fit` on a swapped image.** There is no correct value — `cover` crops a logo, `contain` letterboxes a photo — and a visible distortion is the right signal that the wrong file was picked. The readme says: give the Alt the same dimensions.
- **A zone applies only while its section is on screen**, showing the opposite of the page baseline. No zone carries a target of its own, so `set()` inverts an in-view zone rather than being overridden by it — that's what keeps "dark page with light interludes" working from either side, and it's the seam the dark-mode toggle inherits.

## Sibling-plugin interop

- **Colors compose for free wherever a sibling routes them through Elementor `selectors`.** `Control_Color::get_default_settings()` returns `'global' => ['active' => true]` unconditionally, so the Globals picker is opt-OUT: any plain COLOR control is linkable, and a linked value compiles to `var(--e-global-color-X)`, which our body-level `color-mix` then animates.
- **Header Engine's sticky recolor outranks us, by design.** Its "Recolor While Sticky" repeater emits `--e-global-color-{{global_id.VALUE}}: {{VALUE}}` on `.arts-header_sticky … .arts-header__bar` with a flat static value (`global => active: false`), so a global remapped there stops responding to Alt for as long as the header is stuck — through the hide/reveal slide too, since the selector keys on `_sticky`, not on scroll direction. Correct cascade behaviour and opt-in (empty repeater by default, sticky modes only), but a real two-plugin surprise. Documented in readme.txt, not fixed.
- **We never swap page DOM.** Our only writes are attributes and styles; the `arts/ajax/transition/sync/before` listener calls `coordinator.destroy()` and nothing else. So cleaning up other plugins' instances on a swap is NOT ours to do — that belongs between them and the transitions package.
- **Do not reach for `editor.addControlView()`.** Fluid DS registers its own view for `global-style-repeater`; our Alt swatch stays collision-free precisely because it is PHP-only field injection rendered through the stock view.
- **The family idiom for cross-plugin coupling is a one-way attribute**, not an API: immersive-lightbox marks its root with Header Engine's own `data-arts-header-hide-over="in-view"` and neither imports the other. Mirror that shape if a zone ever needs to be marked or excluded by another plugin.

## Gotchas

- **Never scope panel CSS to a control's TYPE name.** It matched nothing here, and a custom property declared there resolved to an invalid value everywhere it was used — which paints as nothing at all rather than erroring. Use the control's NAME class (`.elementor-control-color_alt`) or declare on the elements themselves (comment in `Assets::enqueue_editor_panel_css()`).
- **The editor bundle is enqueued with no dependencies**, the family idiom, so it also runs BEFORE `window.elementor` exists. Reading the bare `elementor` binding there throws a `ReferenceError` — optional chaining guards a null value, never an undeclared one. So `elementor` and `wp` go through `window.` at module scope, and `elementor/init` (the native event name, slash not colon) is when the app is there. `$e` is the one bare binding that is safe, and not by luck: the enqueue-order proof is in `src/ts/editor/globals.d.ts`. It is an implementation detail rather than a committed contract — moving this plugin's hook or its priority is what would break it.
- **A PHP test that asserts on registration calls `Controls_Manager::delete_stack()` before `get_controls()`**, or it reads whichever stack the first case happened to build (`fresh_controls()` in `AltMediaTest`). A test that seeds kit settings must restore them too.
- **Elementor's frontend handler `Base` calls `onInit()` from its own constructor**, which runs BEFORE a subclass's field initializers. A listener held in a class field is still `undefined` at `addEventListener` time, so the subscription silently binds nothing — no error, no listener. Subscribe as an EventListener object (`addEventListener(type, this)` + a prototype `handleEvent`). `tests/ts/zoneHandler.dom.test.ts`'s fake reproduces that ordering on purpose; keep it that way or this class of bug goes invisible again.
- **Breakpoint changes reach handlers only through `resize`.** Elementor does fire an `elementor/device-mode/change` CustomEvent, but on the TOP editor window — it never reaches a handler living in the preview iframe or on the frontend. The watch belongs to the zone handler, never the coordinator: a zone that switches itself off at a narrow breakpoint leaves the coordinator with no zones to watch, and nothing could bring it back on a wider screen.
- **`add_responsive_control()` puts the top-level `default` on the DESKTOP duplicate only** — it moves it to `desktop_default` and passes no `default` to the tablet/mobile duplicates unless you also give `tablet_default`/`mobile_default`. So `arts_cs_enabled_tablet`/`_mobile` already resolve to `''` on untouched elements, and only the bare desktop key carries `'none'`.
- **Responsive inheritance is client-side, in `getDeviceSetting()`, and keys off truthiness.** It walks from the current device up: a truthy per-device value returns immediately, a falsy one (`''`, or simply absent) keeps walking. That is the whole mechanism behind "`arts_cs_enabled` must be a SELECT" above — `'none'` is truthy, so it stops the walk and stays off; `''` would not.
- **`boot.ts` gates handler attachment on a regex over `data-settings`, outside the editor only.** In the editor the `isEditMode()` escape gives every container a handler, and that is the cost of editing; the docblock above `attach` in `boot.ts` has the reasoning.
- **A 1px strip, never 0.** `rootMargin` insets that collapse the root to zero height make the observer report nothing — this plugin shipped that bug once, with a `-100%` margin at trigger point 0. `coordinator.rootMarginFor()` clamps for exactly that reason, and a test pins the string.
- **Observer state is delivered asynchronously.** IO batches its callbacks, so a probe that reads `getTheme()` immediately after a programmatic `scrollTo` can still see the previous state; it settles within a frame or two. Invisible behind the 0.4s morph, but live tests need a wait after a jump.
- **Horizontal Scroll 1.2.1 is the floor for panel scrubs in the editor.** Up to 1.2.0 it never stamped `--arts-hs-panel-start/end` in the canvas, so a panel scrub ran over `distance × the whole pin` there and over the panel's real window on the frontend — [issue #6](https://github.com/artkrsk/horizontal-scroll-for-elementor/issues/6), fixed.
- **Their horizontal engine is per-breakpoint too**, and both states are handled without a special case: the observer strip means the same thing on either axis, so when their track goes `static` a panel is just an ordinary vertical zone. Only the scrub needs the branch, and it is gated on the `sticky` probe rather than on the plugin's presence. A marked *wrapper* (the whole horizontal section) stays on our own tier deliberately — its runway scrolls normally, so its Viewport handles keep their literal meaning; `closest()` matches the element itself, which is why the branch tests for the TRACK.
- **Arts Horizontal Scroll integration rides their committed contract**: the surface we use, and the contract number it assumes, are listed in `src/ts/constants/HORIZONTAL.ts`, and `core/scrollDriver.ts` reads either `window.artsHorizontalScroll` or the older `window.ARTS_HS`. A contract bump on their side is a review trigger here. Their timeline is used because a block-axis scrub cannot advance while a panel is pinned — it would finish during the section's entry and hold flat across the traversal.
- **Cancelling an animation restores the base value in the same frame and starts no transition.** A scrub handing back to the cascade cut instantly until `scrollDriver.teardown()` began pinning the held value inline for one frame before releasing it.
- **`custom` belongs in every `size_units` set that feeds a `selectors` rule.** It lets an author type a whole CSS value (`clamp(…)`, a `var()`); drop `%` where a percentage would resolve against a shrink-to-fit box and mean nothing. `arts_cs_viewport` is the deliberate exception (`%` alone): it carries no `selectors` at all, and the handler reads its two handles as numbers it clamps to 0–100 — a typed CSS value has nowhere to go.
- **The range slider prints its handle values below the track, over whatever the control renders underneath** — hence the separate `RAW_HTML` hint row and the 36px bottom padding, rather than the slider's own `description`.
