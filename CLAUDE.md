# CLAUDE.md

Guidance for Claude Code working in **Arts Color Switcher for Elementor**.

## What this is

Scroll-triggered palette switching for Elementor. Every Global Color gains an **Alt** value, one registered scalar (`--arts-cs-p`, 0→1) morphs the whole page between the two, and sections marked as *zones* drive that scalar as they cross a trigger line.

Shape: a TypeScript engine (`src/ts/`) over a thin PHP shell (`src/php/`) that registers controls, enqueues assets and renders the toggle's markup — every color is computed in CSS, emitted through Elementor's own kit control `selectors`, so anything already linked to a Global Color animates for free.

Raster images ride the same seam: every image `MEDIA` control on the site is re-typed to `arts_cs_media`, which carries an Alt file as extra sub-keys of the control's own value and emits it through Elementor's `selectors` — no HTML filtering, no DOM writes.

It deliberately ships NO palette of its own and NO per-zone target theme: a zone always shows the opposite of the page baseline — the seam the dark-mode toggle drives by moving the baseline, so every zone inverts with it.

## Config gotchas

- **`biome.json` is NOT JSONC — comments make it invalid.** Biome then falls back to its built-in defaults and silently reformats the whole tree (tabs, double quotes, semicolons), including files your `files.includes` was meant to protect. `biome check` does report the parse error, so read its output rather than tailing it. `knip.jsonc` and `.fallowrc.jsonc` *do* take comments; use them for per-entry reasoning.
- **Adopting a shared config means merging it, not replacing it.** Repo-specific entries hide in these files — a security `overrides` pin, a plugin-check ignore code, an extra workflow trigger. Diff the old file against the new one before deleting anything; CI will not tell you what you dropped.
- **Any dependency with an install script needs an explicit `allowBuilds` decision.** pnpm only warns locally but fails CI. Adding `@wordpress/env` is the usual trigger — see the commented entry in `pnpm-workspace.yaml`.
- **`composer.lock` resolves dev deps against YOUR PHP, not `Requires PHP`.** The canary runs that same vendor tree under PHP 8.0, where doctrine/instantiator 2.1.0 (typed class constants, `"php": "^8.4"`) fatals on the first `createMock()`. Hence the `^1.5` pin in `require-dev`; the repo runs PHPUnit now (`tests/php/`), so the pin is already load-bearing — keep it while the floor is 8.0.

## Architecture

- **`src/php/Plugin.php`** — composition root. Extends `Base\Plugin` (arts/base `BasePlugin`), runs on `plugins_loaded` priority 20, wires the managers: `assets` (handles, the polyfill dependency, the pre-paint head script), `documents` (page-theme control + the baseline attributes), `elements` (the container/section control section), `elementor` (one Elementor cache clear per plugin version, widget registration), `kit` (Alt swatch injection), `media` (the Alt image control), `toggle` (every skin's markup + the shortcode).
- **`src/php/Controls/AltMedia.php`** — `Control_Media` subclass, type `arts_cs_media`. Owns the Alt sub-keys, the panel's words (as a control arg, so they stay translatable), and `get_style_value()`.
- **`src/php/Managers/Media.php`** — registers that control and re-types every image media control on the site as each section closes.
- **`src/ts/editor/altMedia.ts`** — the editor view: injects the Alt button into the stock control's own tools row and owns a second `wp.media` frame.
- **`src/php/Widgets/Toggle.php`** — the visitor-facing control, one widget with four Elementor skins in `Widgets/Skins/`. The skins are adapters: each calls `render_skin()`, which calls the `toggle` manager, so the shortcode draws exactly the same shapes.
- **`src/ts/boot.ts`** — frontend entry. Registers the `element_ready` hooks, gates handler attachment on a `data-settings` regex outside the editor, publishes `window.ArtsColorSwitcher`.
- **`core/zoneHandler.ts`** — the Elementor frontend handler: control values → an `IZone`, and it owns the resize/breakpoint watch.
- **`core/coordinator.ts`** — page-level state owner. Holds every zone, owns every IntersectionObserver, writes the ONE `<html>` attribute.
- **`core/resolve.ts`** — pure. Zone snapshots + baseline → `{ theme, scrubbingIndex }`, no DOM.
- **`core/scrollDriver.ts`** — the scrub, in three tiers: Arts Horizontal Scroll's published timeline, native CSS view-timeline, then WAAPI over the shared polyfill.
- **`core/horizontal.ts`** — all Arts Horizontal Scroll interop, in one place because the coordinator and the scroll driver must agree on it.
- **`core/preference.ts`** — the visitor layer. Owns the cookie (`write()` / `clear()` are its only writers) and mirrors it onto `<html>`.
- **`core/toggle.ts`** — every skin's presses and announcements. Skins differ only in how a press maps to a preference; what looks active is CSS's job.
- **`editor/index.ts`** — its own bundle: one `hookUI.After` over `document/elements/settings` that keeps the preview honest.

## Decided — don't reintroduce or "fix"

- **`arts_cs_enabled` is a `SELECT` (No/Yes), not a `SWITCHER`.** A switcher's off state is `''`, which Elementor's responsive inheritance reads as "unset" (so mobile inherits the desktop "on") and which `get_frontend_settings()` drops entirely. Both states must carry a real value or "off on mobile" is inexpressible.
- **`arts_cs_viewport` is NOT responsive.** `add_responsive_control()` seeds each breakpoint's duplicate with the plain slider's empty value (`{unit:'px', size:'', sizes:[]}`) instead of a `{start,end}` pair, so the range renders as a single-handle slider below desktop. The control args survive fine — it's the value seeding, so no amount of declaring fixes it. The per-device need is "don't run it here", which the enable control covers.
- **Zone state comes from an IntersectionObserver, never from a scroll listener.** The trigger line IS the observer's root, collapsed to a 1px full-width strip. That is what makes zones correct on both axes: a panel pinned inside a horizontal track has a frozen vertical band and moves only sideways, so a `getBoundingClientRect()` comparison reports it as on screen for the entire pin. Do not reintroduce a scroll pass — performance was never the reason; correctness was.
- **Inside a pinned horizontal track the strip is ROTATED** — a 1px column across the stage rather than a row across the viewport — so the Viewport handles keep the meaning they have vertically: how far into the screen the section travels before switching. Without it the handles decided nothing there, because a pinned panel spans the whole track height for its entire traversal and any horizontal line is always crossed. The line is measured across the WRAPPER, never the track: the track is the full max-content row of panels and it is the thing being translated, so a line on it slides along with the content it is meant to measure. Measuring on the wrapper also survives a boxed section and any edge gutter — the editor canvas has one, and a line pinned to viewport x=0 sat inside it and never matched.
- **The strip is full-width on purpose** (upright case). A centre-point root (the sibling plugin's scrollspy trick) would give free exclusivity between horizontal panels, but a vertical zone narrower than half the viewport would then never intersect it.
- **The frontend bundle is enqueued unconditionally.** There was a gate that grepped `_elementor_data` for a marked section; it cost a `json_decode` plus a full `wp_json_encode` of the document on every request to withhold a few KB gzipped, and its affordable needle — the bare word `switch` — matched most documents that had no zone at all. The bundle is inert without zones now that boot gates its own handler attachment, so the cheap thing is to ship it. Do not reintroduce a document-data gate.
- **Authority runs visitor, then author, then device.** A cookie always wins; its PRESENCE is what transfers authority. With no cookie the page's own setting decides, and only where the author declined to set one — `arts_cs_page_theme` on its `THEME_AUTO` default — does the device get a say. The device is last rather than absent because it is the only party that knows the visitor's real sunrise and sunset; that is also why there is no scheduling feature and never will be, since a server has one clock and its visitors do not. Before 1.0 the device had no say and the author's baseline won outright, which left several sites already treating no-cookie as `system` while `resolveBaseline()` alone disagreed — the three-state page control resolved that split. The precedence table is stated twice, in `resolveBaseline()` and in the head script PHP composes; `tests/ts/headScriptParity.dom.test.ts` executes the real emitted script against the real resolver over every combination, because if they drift the page changes theme between first paint and boot.
- **A two-state control releases, it does not pin forever.** Press once to store a choice, press again to DELETE the cookie — putting the visitor back exactly where they were before their first press, which is the one place a two-state control can return them to. Deliberately not `write('system')`: what that place IS depends on the page (the author's palette where they pinned one, the device's where they did not), and either way it is somewhere the visitor has already been. That is the whole two-state-vs-tri-state argument, and the authority rule above leaves it unaltered.
- **The editor canvas never follows the author's device.** `followsDevice()` in `coordinator.ts` gates the Auto resolution on `isEditMode()`. Without it an author on a dark machine opens a light page, finds it dark, and designs against colors none of their visitors asked for. The OS watcher is safe for free because it calls `coordinator.refresh()` rather than forcing a theme — one precedence table, one place it can be wrong.
- **A control inverts the BASELINE, never `getTheme()`.** A zone on screen shows the opposite of the baseline, so reading the applied theme there stores the opposite of what the visitor asked for: the first press appears to do nothing and the second brightens the page. `coordinator.getBaseline()` exists for this and is deliberately NOT on the public contract.
- **What looks active is decided in CSS off `<html>`, not by the script.** The head script stamps `data-arts-cs-pref` before first paint, so a cached page never shows one visitor's control in another's state. The Switch's knob is a different mechanism in the same spirit: it rides `--arts-cs-p` itself (`--arts-cs-seg-index: var(--arts-cs-p)` on its track — still CSS, zero script), so it glides in lockstep with a binary morph and literally tracks a scrub, which the attribute deliberately never flips for (`resolve.ts`: flipping it would snap the scalar); every scrub tier animates the scalar on body and it inherits, so this holds inside a pinned horizontal track too. Its transform transition is zeroed in `_switch.scss` — the shared 0.3s would chase per-frame scrub values — and its icon paint rides the same scalar through the control-emitted blends (see the hover bullet below). Only `aria-checked` stays discrete off `data-arts-cs`; ARIA cannot meaningfully interpolate, and that is accepted. The one exception is the Dropdown — CSS cannot SET a `<select>`'s value, the price of the platform's own keyboard and touch handling, so `toggle.ts` corrects `select.value` at boot. (Where customizable selects are supported CSS READS it — `option:checked` marks the chosen row — but no `selected` attribute is printed, so that row is the first option until boot; invisible in practice, since the picker cannot be open before then.)
- **The Dropdown's list is a customizable-select enhancement, gated by `@supports (appearance: base-select)`.** SCSS owns the opt-in and the zero-config card in `_dropdown.scss` (browsers without support keep the platform picker, safely outside the gate); the List section owns author values. The card is `Canvas`/`CanvasText` plus `currentcolor` mixes because the plugin ships no palette — the `color-scheme: dark` flip in `_state.scss` is what turns it. The checked row's fill rides `--arts-cs-toggle-active` via `INDICATOR_SKINS` (`ACTIVE_SKINS` deliberately NOT widened — it gates the segmented geometry's `track_padding`, dead on a skin with no track); its hover selectors exclude `:checked`; `gap` is hidden on the dropdown (`_skin!` — the root's only child is the select). Never comma-join a `::picker()`/`::checkmark` selector into a legacy key (`BOX`, `LABEL`, `OPTION`): a browser without the pseudo drops the whole list, taking the legacy rules with it — `PICKER`/`LIST_OPTION` exist so modern selectors stay in their own keys.
- **ARIA follows the visual affordance.** `role="switch"` only on the Switch skin, `aria-pressed` on the Icon and Buttons skins: switch support is inconsistent enough (Firefox/NVDA does not announce it as a switch at all) that a pressed button is the safer reading of anything that looks like a button. The Buttons skin is `role="group"` + pressed buttons rather than a radiogroup, because a radiogroup must have a selection and this one deliberately may not — "neither pressed" is how two options express the third state.
- **Joined and Separate are told apart by movement, not chrome.** Joined is one track with a single mark that travels to the pinned option; Separate is independent buttons where the pinned one carries its own fill. Both were once a border and a gap apart, which read as the same control with different padding.
- **The segmented geometry is derived, never hardcoded** — the same model as the pricing switcher in `~/Projects/ArtsStore`, which is the same control. Three numbers state it: `--arts-cs-seg-pad`, `--arts-cs-seg-gap` and `--arts-cs-seg-count` (emitted inline by PHP, since the count is the one thing CSS cannot work out). The mark's width is `(100% - pad*2 - gap*(N-1)) / N` and its travel is `index * (100% + gap)` — one column PLUS one gap, which halves and thirds hardcoded per mode got wrong the moment a gap existed. Percentages resolve against the padding box, so the same formulas hold with or without a border. The Spacing control writes `gap` AND `--arts-cs-seg-gap` for that reason.
- **There are no divider lines — a seam is the buttons' own borders meeting, and "flush" is derived, not queried.** Joined once drew dividers derived from its track border; they were cut (the travelling mark already marks the boundaries, and mixing them with Separate's per-button borders read as two line systems). In Separate, `--arts-cs-seg-flush: calc(var(--arts-cs-seg-gap) * 9999)` is 0 flush and effectively infinite at any spacing, so `min(value, flush)` states "only while flush" as arithmetic — no style query, every browser. Flush, each `+` sibling's left border-width collapses to 0 (the previous button's right border IS the 1px seam — suppression, not overlap, because two stacked translucent borders composite darker) and inner corners square off so seams stay straight; `:first-child`/`:last-child` restate the group's outer corners plainly. The `min()` rules are emitted by the controls themselves (`option_border` `fields_options`, `option_radius` selectors): a plugin-stylesheet longhand can never outrank the `{{WRAPPER}}`-scoped shorthand it must beat.
- **Those variables are declared on the ROOT, not the track.** Custom properties inherit, and the track is not always the same element: the Joined root IS its own track, the Switch's is a child. Re-declaring them on the track is what made the Spacing control dead on the Switch — the track overrode the value before it could arrive.
- **The track is an inline GRID, not a flex row.** `grid-auto-columns: 1fr` makes every column the width of the largest even when the box is shrink-to-fit; `flex: 1 1 0` does not, because an inline flex container has no free space to distribute and every option keeps its own content width. Nothing is given a size either — the Switch track is what its icons make it, so Icon Size, Track Padding and Spacing are its only dimensions, and the mark's colour is one custom property (`--arts-cs-toggle-active`) so a single control reaches it wherever the layout puts it.
- **Empty means absent, and the state count is STATED, never derived.** The label controls carry real defaults an author can delete rather than placeholders, and deleting one prints nothing — including an empty `<option>` in the Dropdown. How many states a control offers is the `mode` control, offered to every skin but the Switch (a knob has no third position); it was once derived from whether the System label had a word, which held while a word was all an option could be and broke the moment icons made an icon-only option legitimate — clearing the label to drop the text deleted the option with it. A Buttons option with no icon and no word falls back to the announced name rather than rendering empty. The built-in words (System / Light / Dark) survive only as the ANNOUNCED name, where no author can see them and an unnamed control would be unusable. The panel keeps the Default/Alt vocabulary in its control names; what a visitor reads says Light and Dark.
- **Style controls live on the WIDGET, in one Normal / Hover / Active tabs group — never in the skins.** `Skin_Base::start_controls_tabs()` assembles a `_skin` condition into a local variable it then never passes on (`parent::start_controls_tabs( $id )` takes the id alone), so the tabs WRAPPER is registered unconditioned while every tab header and field inside it is correctly scoped. Four skins each opening a group would leave three empty tab wrappers in the panel — and all four write `current_tab` on one shared stack, where a callback that fails to close its tabs takes the next skin down with a `wp_die`. Declared on the widget there is one group, one owner, and plain `_skin` conditions do the scoping. `Controls_Stack::start_controls_tabs( $id, array $args = [] )` DOES accept args, so a tab header can be conditioned — the Active tab is, since an icon that is the whole control has no "other" to be distinguished from. The skins are now `get_id`/`get_title`/`render` and nothing else.
- **No built-in state dimming.** The skins put no opacity of their own on icons or words — the 0.5 on the Buttons options and the 0.45 on the Switch's off icon were cut, because a dim composing on top of the colour controls means the Normal colour an author picks is never the colour that renders, with no control to say otherwise. Every state those dims faked is expressible through the existing Normal/Hover/Active colour controls; the zero-config marks are structural instead — the knob's position, the pinned option's fill, the Icon skin's swap. (The Buttons dim was also the root of a flush-group artifact: per-option opacity faded three of a hovered cell's borders and left its leading seam at the neighbour's strength, since that seam is the neighbour's border.) Mechanical opacity stays — the hidden knob, the dropdown card's open animation.
- **Hover never repaints what is already chosen.** The Buttons skin states this as selector correlations between the `<html>` attribute and the element's own — the lists composed by `Widgets\Toggle::option_states()` and the `icon_hover()` / `icon_active()` / `label_hover()` / `label_active()` methods. The Switch states it as ARITHMETIC: its icon paint is a `color-mix` of the author's Normal/Active/Hover values weighted by `--arts-cs-p`, blended in `_switch.scss` off vars (`--arts-cs-sw-icon{,-hover,-active}`) the colour controls emit on the Switch root — hover pushes by how NOT-chosen the icon is, so a fully chosen icon is untouched by construction. Never key Switch paint off `data-arts-cs` (a scrub deliberately never flips it, so attribute-keyed paint lit the wrong icon for the whole band a scrub held), and never put the blend in a control's value template: **a Global-linked value BYPASSES `{{VALUE}}` templates** — `add_control_rules()`, reached via `add_control_style_rules()`, rewrites everything between `:` and `;` to the bare global var (elementor `core/files/css/base.php`), so only `property: {{VALUE}}` shapes survive linking. It compiles fine with a literal hex and collapses the moment a Global is linked, which is why the e2e seed alone cannot catch it. And never gate anything on a STYLE QUERY over the scalar (`@container style(--arts-cs-p: …)`): Firefox does not re-evaluate style queries when an inherited animated property changes, in either direction — a `pointer-events` guard stuck wrong both ways and bricked the control. Chromium invalidates correctly; one broken engine killed the idea.
- **Condition a section AND every control in it, for two different reasons.** `get_style_controls()` filters through `is_control_visible()` (`core/files/css/base.php`), so a control whose condition fails emits NO CSS — that is what stops a skin's rules being generated for the three skins that do not use them. A section's condition only decides what an author sees; it does not gate CSS.
- **A section's `condition` is merged into every control in it with `array_replace_recursive`, which merges lists BY INDEX.** `get_section_args()` (`controls-stack.php`) copies the section's `condition` onto each control, and `handle_control_position()` merges the two — so a two-skin list inside a three-skin section keeps the section's third entry and silently widens. A scalar replaces cleanly; a shorter list does not. `conditions` (plural) is NOT copied into a section's args, so state it that way whenever a control's set is narrower than its section's — `Widgets\Toggle::icon_active_conditions()` exists for exactly this. Every nested condition in that file is composed from three builders (`any()`, `all()`, `term()`) rather than written out as literals; `term()` OMITS the `operator` key when there is no operator, because `Conditions::check()` reads `! empty( $term['operator'] )` and falls through to a strict `===`, and one shape is one fewer thing for PHP and the editor's JS to disagree about. `DarkModeTest::test_every_nested_condition_states_its_full_shape()` pins those arrays in full — the other assertions in that file only substring-match the JSON, which cannot see term order or a dropped operator.
- **A tab carries no `selectors`,** so Optimized Control Loading files it as a style control and `get_controls()` never returns it. A test that reads tab structure has to run under the editor's conditions (`Performance::$is_frontend` false) and rebuild the stack, not just flip `set_use_style_controls()`.
- **No widget control ever takes a colour PAIR.** A "Track Color (Alt)" existed briefly on the Switch skin and was cut: a second colour for the other theme is the per-element two-value configuration this plugin exists to remove. Every colour control takes one value, the author links it to a Global Color, and the Alt swatch in Site Settings turns it — which is the whole architecture, and the reason the plugin ships no palette of its own.
- **A control whose effect the author cannot see is not offered.** The label controls appear only on the Buttons and Dropdown skins, which print the words; on Icon and Switch they would change the tooltip and what a screen reader announces, which reads as a dead control in the panel. There is no control for the group's accessible name at all, for the same reason. Both still render — from the translated defaults — so nothing is unnamed. The shortcode keeps them all: it is a power-user surface, not a panel.
- **Visitor-facing words come from PHP, never from the script.** They were hardcoded English in `toggle.ts` and spoke the author's vocabulary ("Alt colors" names a slot in Site Settings and means nothing to a reader). PHP renders them into `data-arts-cs-label-*` where TS reads them: translatable through the normal .po path, with no `wp_set_script_translations` and no JSON translation files to ship — and authorable, which covers the site whose Alt palette is the lighter of the two.
- **Alt images RE-TYPE the media control; they do not add a sibling.** Same shape as `~/Projects/Framework/packages/ArtsEnhancedURLControl`, which does it for every URL control in production. A new type name is also why `elementor.addControlView` cannot bite: last-write-wins only matters when two plugins claim the same key, and only we claim ours. Never override the stock `media` type. The one cost is real: core's atomic-widget dynamic-tag conversion dispatches on the literal string `'media'` (`modules/atomic-widgets/dynamic-tags/dynamic-tags-editor-config.php`), so a re-typed control drops out of it — every other core path gates on `instanceof Base_Data_Control` and is untouched. Inert unless Atomic Widgets is on; it is the standing argument for a sibling control if it ever bites.
- **Everything is upgraded once any Alt swatch exists (`has_alt_colors()`, same gate as the head script); the per-control test is `media_types` containing `image`.** No widget allowlist. An Alt for a video or file picker means nothing, and Elementor AI applies the same test before offering its own media button.
- **The scan reads BOTH stack buckets, never `get_controls()`.** `add_control_to_stack()` files a control carrying `selectors` into `style_controls` whenever `Performance::should_optimize_controls()` is true, and `get_controls()` merges that bucket back only while `Performance::is_use_style_controls()` is true — which is only during a CSS file rebuild. Two independent flags, so a bare read is blind to `background_image` on a frontend request, which is the control that most needs seeing. `Controls_Manager::get_element_stack()` returns both.
- **A re-typed control carries `control_type => 'content'`.** Adding `selectors` to one that had none — the Image widget's own — would otherwise make it a style control and move it out of the bucket `parse_dynamic_settings()` iterates, so a dynamic-tagged image would silently stop resolving at render. `is_style_control()` returns false outright for that arg, and CSS is still generated because the generator keys only on the presence of `selectors`. Core marks its own background `color` field the same way.
- **The Alt rule is DERIVED from the control, never written here.** A declaration containing `{{URL}}` is mirrored verbatim under `html[data-arts-cs="alt"] ` with the placeholder swapped, so this plugin names no CSS property and covers `background-image`, `video_fallback` and anything a widget invented. A control with no declaration prints an `<img>`, so it gets `content: url(...)` on `{{WRAPPER}} img` — replaced-element content, universal since Firefox 63. That second branch is correct only for single-image widgets; carousels and galleries are deliberately out of scope, and if per-image precision is ever needed the hook is `elementor/image_size/get_attachment_image_html`, NEVER `render_content`.
- **Originals stay FIRST in the merged `selectors` array.** When a placeholder resolves to `''` with no `||` fallback, `Files\CSS\Base::add_control_rules()` throws and RETURNS, abandoning that control's remaining selectors. An unset Alt costs the widget nothing only because its own rules are already written by the time ours bails. Pinned by generating real CSS, not by asserting array order.
- **The kit is skipped by the scan outright.** Its tabs are `Sub_Controls_Stack` proxies that forward `end_controls_section()` to the kit, so a tab closing fires the scan with the KIT as the registering stack, mid-`register_controls()`. Reading the Alt-swatch gate there re-enters `Base_Object::ensure_settings()`, which caches only once `get_init_settings()` returns — so the nested read caches a half-registered snapshot of the kit's settings for the rest of the request. Bounded, not infinite, and still not worth an Alt picker on the Site Logo.
- **The Alt resolves through the attachment, like the parent's own URL.** `Control_Media::get_style_value()` special-cases `URL` and returns `wp_get_attachment_image_url( $id, $size )`; the Alt does the same or the pair renders at two different resolutions. A deleted attachment falls back to the stored URL rather than emptying the rule.
- **Images swap abruptly; there is no cross-fade.** Keyed off `data-arts-cs`, which a scrub deliberately never flips, so an image holds through a scrubbing zone and swaps only on a settled transition. A fade needs a second painting surface (`::before` is Elementor's Background Overlay) and is a real v2 — and the escape hatch you would reach for, a style query over `--arts-cs-p`, is already ruled out above.
- **No `object-fit` on a swapped image.** There is no correct value — `cover` crops a logo, `contain` letterboxes a photo — `includes/widgets/image.php` already emits `{{WRAPPER}} img => object-fit` from the widget's own control, and a visible distortion is the right signal that the wrong file was picked. The readme says: give the Alt the same dimensions.
- **A zone applies only while its section is on screen**, showing the opposite of the page baseline. No zone carries a target of its own, so `set()` inverts an in-view zone rather than being overridden by it — that's what keeps "dark page with light interludes" working from either side, and it's the seam the dark-mode toggle inherits.

## Sibling-plugin interop

- **Colors compose for free wherever a sibling routes them through Elementor `selectors`.** `Control_Color::get_default_settings()` returns `'global' => ['active' => true]` unconditionally, so the Globals picker is opt-OUT: any plain COLOR control is linkable, and a linked value compiles to `var(--e-global-color-X)`, which our body-level `color-mix` then animates. Nothing to build — this is the architecture paying off, and it is the reason not to invent a palette of our own.
- **Header Engine's sticky recolor outranks us, by design.** Its "Recolor While Sticky" repeater emits `--e-global-color-{{global_id}}: {{VALUE}}` on `.arts-header_sticky … .arts-header__bar` with a flat static value (`global => active: false`), so a global remapped there stops responding to Alt for as long as the header is stuck — through the hide/reveal slide too, since the selector keys on `_sticky` alone. Correct cascade behaviour and opt-in (empty repeater by default, sticky modes only), but a real two-plugin surprise. Documented in readme.txt, not fixed.
- **Its admin-bar handling independently agrees with ours** — same `--wp-admin--admin-bar--height`, same `body.admin-bar` gate, same 600px cutover. Independent corroboration that our own admin-bar metric is right.
- **We never swap page DOM.** Our only writes are attributes and styles; the `arts/ajax/transition/sync/before` listener calls `coordinator.destroy()` and nothing else. So cleaning up other plugins' instances on a swap is NOT ours to do — that belongs between them and the transitions package. (Raised for device-mockups, declined for this reason.)
- **Clean, no interaction**: smooth-scrolling (Lenis on `window` — real native scroll, so observers and view-timelines behave normally), immersive-lightbox (body child, `overflow: clip` lock with no `position: fixed`), fluid-design-system (own Site Settings tab, `:root`/`arts-fluid` scope), repeater-tags (no frontend JS at all).
- **Do not reach for `editor.addControlView()`.** Fluid DS registers its own view for `global-style-repeater`, where last registration wins; our Alt swatch stays collision-free precisely because it is PHP-only field injection rendered through the stock view.
- **The family idiom for cross-plugin coupling is a one-way attribute**, not an API: immersive-lightbox marks its root with Header Engine's own `data-arts-header-hide-over="in-view"` and neither imports the other. Mirror that shape if a zone ever needs to be marked or excluded by another plugin.

## Gotchas

- **A control's root class is `elementor-control-{NAME}`; the TYPE only appears as `elementor-control-type-{type}`.** Scoping panel CSS to a type name matches nothing, and a custom property declared there resolves to an invalid value everywhere it is used — which paints as nothing at all rather than erroring. Declare on the elements themselves.
- **The editor bundle is enqueued with no dependencies**, the family idiom, so it also runs BEFORE `window.elementor` exists. Reading the bare `elementor` binding there throws a `ReferenceError` — optional chaining guards a null value, never an undeclared one. So `elementor` and `wp` go through `window.` at module scope, and `elementor/init` (the native event name, slash not colon) is when the app is there. `$e` is the one bare binding that is safe, and not by luck: `elementor-common` (which depends on `elementor-web-cli`, where `window.$e` is assigned) is enqueued at priority 9 of `elementor/editor/before_enqueue_scripts` while ours is at 10, and `elementor-editor` joins the queue only after that action returns — all in_footer with no `strategy`, so DOM order is execution order. Implementation detail rather than a committed contract: moving this plugin's hook or its priority is what would break it.
- **Elementor caches a control stack per element TYPE for the whole process**, so a test that asserts on registration reads whichever stack the first case happened to build. `Controls_Manager::delete_stack()` before `get_controls()`. The kit DOCUMENT is cached the same way and WP's rollback only restores the database, so a test that seeds kit settings must restore them too.
- **Elementor's frontend handler `Base` calls `onInit()` from its own constructor**, which runs BEFORE a subclass's field initializers. A listener held in a class field is still `undefined` at `addEventListener` time, so the subscription silently binds nothing — no error, no listener. Subscribe as an EventListener object (`addEventListener(type, this)` + a prototype `handleEvent`). `tests/ts/zoneHandler.dom.test.ts`'s fake reproduces that ordering on purpose; keep it that way or this class of bug goes invisible again.
- **Breakpoint changes reach handlers only through `resize`.** Elementor does fire an `elementor/device-mode/change` CustomEvent, but on the TOP editor window — it never reaches a handler living in the preview iframe or on the frontend. The watch belongs to the zone handler, never the coordinator: a zone that switches itself off at a narrow breakpoint leaves the coordinator with no zones to watch, and nothing could bring it back on a wider screen.
- **`add_responsive_control()` puts the top-level `default` on the DESKTOP duplicate only** — it moves it to `desktop_default` and passes no `default` to the tablet/mobile duplicates unless you also give `tablet_default`/`mobile_default`. So `arts_cs_enabled_tablet`/`_mobile` already resolve to `''` on untouched elements, and only the bare desktop key carries `'none'` — `data-settings` never contains a device-suffixed variant unless it was explicitly set.
- **Responsive inheritance is client-side, in `getDeviceSetting()`, and keys off truthiness.** It walks from the current device up: a truthy per-device value returns immediately, a falsy one (`''`, or simply absent) keeps walking. That is the whole mechanism behind "`arts_cs_enabled` must be a SELECT" above — `'none'` is truthy, so it stops the walk and stays off; `''` would not. PHP does no inheritance at all, it resolves each breakpoint's control independently.
- **`data-settings` is written by PHP once and by nothing else, ever.** Its only writer in Elementor is `Element_Base::add_render_attributes()`; no editor JS refreshes it on re-render. On the frontend it IS the handler's read path (`Base` resolves through `$element.data('settings')`), which is what lets `boot.ts` gate handler attachment on a regex over it — `addHandler` always constructs, so gating has to happen before the call. In the editor `getElementSettings()` reads the live model instead and the attribute is stale, hence the `isEditMode()` escape: there every container gets a handler, and that is the cost of editing.
- **A 1px strip, never 0.** `rootMargin` insets that collapse the root to zero height make the observer report nothing — this plugin shipped that bug once, with a `-100%` margin at trigger point 0. `coordinator.rootMarginFor()` clamps for exactly that reason, and a test pins the string.
- **Observer state is delivered asynchronously.** IO batches its callbacks, so a probe that reads `getTheme()` immediately after a programmatic `scrollTo` can still see the previous state; it settles within a frame or two. Invisible behind the 0.4s morph, but it means live tests need a wait after a jump, and it is a real difference from the scroll pass this replaced, which resolved synchronously in rAF.
- **Horizontal Scroll 1.2.1 is the floor for panel scrubs in the editor.** Up to 1.2.0 it never stamped `--arts-hs-panel-start/end` in the canvas (their engine booted while the nested-elements machinery had left the track empty), so a panel scrub ran over `distance × the whole pin` there and over the panel's real window on the frontend — [issue #6](https://github.com/artkrsk/horizontal-scroll-for-elementor/issues/6), fixed. Nothing in our e2e depends on the fix (the cross-plugin specs assert binary zones, which never read those vars).
- **Their horizontal engine is per-breakpoint too**, and both states are handled without a special case: the observer strip means the same thing on either axis, so when their track goes `static` a panel is just an ordinary vertical zone. Only the scrub needs the branch, and it is gated on the `sticky` probe rather than on the plugin's presence. A marked *wrapper* (the whole horizontal section) stays on our own tier deliberately — its runway scrolls normally, so its Viewport handles keep their literal meaning; `closest()` matches the element itself, which is why the branch tests for the TRACK.
- **Arts Horizontal Scroll integration rides their committed contract** (`window.ARTS_HS.contract === 1`): the `.js-arts-hs` / `.js-arts-hs__track` hooks, the `sticky`-track state probe, `getTimeline(el)`, `--arts-hs-panel-start/end`, and `arts-hs:ready` for their late boot. A contract bump on their side is a review trigger here. Their timeline is used because a block-axis scrub cannot advance while a panel is pinned — it would finish during the section's entry and hold flat across the traversal.
- **A skin object is shared per widget TYPE; the control stack is built by whichever INSTANCE asks first.** Only relevant again if a skin ever registers controls, which none do now. `register_skins()` runs on the registered type instance, so a skin holds that instance as `parent` — but in the editor preview a rendered element triggers `init_controls()`, and a `before_section_end` callback then fires while the skin still points at the type instance, which is not inside a section. `handle_control_position()` `wp_die`s there, and silently drops the control when `Performance::should_optimize_controls()` is true — which is why the frontend and PHPUnit looked fine while the editor died. The fix was `set_parent()` on the stack the hook hands you, before adding anything.
- **WP's test case restores `$wp_filter` after every test.** Elementor registers widgets lazily, so the `add_action` calls a skin makes during registration are gone by the next test in the file. A test that depends on those hooks must re-construct the skins itself. No test does now that the skins register no controls, but the ordering still bites: run the whole file rather than a single `--filter`ed method when touching skin registration.
- **Elementor strips editor-only control args (`options`, `handles`, `label`, `description`) from the stored stack outside the editor.** PHPUnit sees only `type/tab/section/frontend_available/responsive/parent/default/name/inheritors`, so assert invariants through those; read the full args from `elementor.config.elements.<type>.controls` in the editor instead.
- **Cancelling an animation restores the base value in the same frame and starts no transition.** A scrub handing back to the cascade cut instantly until `scrollDriver.teardown()` began pinning the held value inline for one frame before releasing it.
- **`custom` belongs in every `size_units` set that feeds a `selectors` rule.** It lets an author type a whole CSS value (`clamp(…)`, a `var()`), and Elementor makes it work by resolving `{{UNIT}}` to `__EMPTY__` — so a selector already written as `{{SIZE}}{{UNIT}}` or `{{TOP}}{{UNIT}}` needs no change. Core's canonical length set is `px, %, em, rem, vw, vh, custom`; drop `%` where a percentage would resolve against a shrink-to-fit box and mean nothing. `arts_cs_viewport` is the deliberate exception (`%` alone): it carries no `selectors` at all, and the handler reads its two handles as numbers it clamps to 0–100 — a typed CSS value has nowhere to go.
- **The range slider prints its handle values below the track, over whatever the control renders underneath** — hence the separate `RAW_HTML` hint row and the 36px bottom padding, rather than the slider's own `description`.
